## Specs

### S14 — B17: el build de referencia no puede reescribir el lock que la key hasheó

La key de compatibilidad del seed hashea el lockfile:

```
scripts/seed_compat_key.sh:129-130
  if [ -f "$REPO_ROOT/Cargo.lock" ]; then
    LOCK_DIGEST="sha256:$(sha256sum "$REPO_ROOT/Cargo.lock" | cut -d' ' -f1)"
```

El build que publica el seed se define en un único lugar:

```
scripts/seed_recipe.sh:440-446
  seed_recipe_cargo_args() {
    printf '%s\n' \
      build --workspace --offline \
      ${SEED_RECIPE_PROFILE:+--profile "$SEED_RECIPE_PROFILE"} \
      ${SEED_RECIPE_TARGET:+--target "$SEED_RECIPE_TARGET"} \
      ${SEED_RECIPE_FEATURES_CANON:+--features "$SEED_RECIPE_FEATURES_CANON"}
  }
```

`--locked` no está. Consecuencia: cargo puede reescribir `Cargo.lock` (un lock desactualizado respecto de los manifests se actualiza durante el build) **después** de que la key lo hasheó → el seed publicado corresponde a una resolución que la key nunca describió, y el consumidor que verifica la key cree que el build es reproducible cuando no lo es.

Requisitos:

1. El build de referencia debe correr con `--locked`, de modo que un lock que no coincide con los manifests **fraciese la publicación** en vez de reescribirse en silencio. El cambio va en `seed_recipe_cargo_args()` —el origen único de los args del build—, no en `seed_publish.sh`, para que todo consumidor de la recipe lo herede.
2. El fallo debe ser **fail-closed y visible**: el error de cargo tiene que llegar al operador. Nada de `|| true`, nada de un subshell que se traga el status. Si la publicación muere, muere con el mensaje de cargo.
3. Invariante a fijar con un test: **el digest del lock que la key registró es el digest del lock que el build dejó en disco**. Si difieren, la publicación no puede continuar.
4. La recipe es la que describe el build, y `--locked` pertenece a la recipe por la misma razón que `--profile` o `--target`: es parte de lo que la key describe. No es una opción del entorno ni un ajuste del shell del operador.
5. **Consecuencia a investigar y reportar, no a absorber en silencio:** si `SeedCompatibilityKey` hashea los args del build, añadir `--locked` cambia la key → los seeds existentes dejan de ser compatibles. El worker debe **determinar y reportar** si la key cambia, y si cambia, dejarlo escrito para el cuerpo del PR (los seeds viejos hay que reconstruirlos). Reportar el hallazgo; no ampliar el cambio por cuenta propia.
6. El lock del repo debe seguir siendo coherente con los manifests: verificar con un comando que **no compila** (`cargo metadata --locked --offline --format-version 1 --no-deps`), que es exactamente el patrón que ya usa `scripts/generate-sbom.sh:169`. Si el lock del repo estuviera desactualizado, `--locked` rompería la publicación legítima y eso hay que saberlo ANTES de tocar nada.

Requisitos:

El harness debe quedar cableado en el job `repo-guards` de `.github/workflows/ci.yml` como paso real, con la forma del repo: `- name: … semantics harness` / `run: bash scripts/test_ci_fast_gate.sh`, junto a los pasos `… semantics harness` que ya existen. Un harness que ningún job corre es la forma #1707 y no prueba nada.
4. El harness prueba el **comportamiento observable** del gate (exit code + mensaje de error), no su texto interno. Un caso por hallazgo, como mínimo: A1 (clasificador roto → el gate falla, no sigue como si nada), A2 (un `.rs` en el diff → la aserción de "no code files" lo detecta), B45 (base irresoluble → el gate elige FULL, no un lane estrecho).
5. El harness no puede depender de la red, ni del estado del repo real, ni de variables de entorno del operador.

### S16 — el harness no compila NADA (presupuesto de recursos)

Este requisito es del dueño, no una preferencia: la auditoría de scripts y sus ejecutores ya deixaram la máquina sin recursos dos veces. Los hechos (Engram, proyecto webfang):

- El incidente de saturación fue **N builds concurrentes**, no un OOM: un gate full-lane de una sesión coincidió con el build de otra misión en otro worktree (`build-saturation/concurrency-policy`, obs #1651). El knob de memoria es el equivocado para saturación de CPU; `oomd` es estructuralmente ciego a saturación de CPU (PSI de memoria 0.00 en todas las cgroups) (obs #1650).
- `CARGO_BUILD_JOBS` está **indefinido** en `.cargo/config.toml`, `mise.toml` y `Cargo.toml` → cargo usa `nproc` = **16** rustc en paralelo (obs #1650).
- El lane full compila BoringSSL (639 objetos C++) y linkea binarios de test de 1,5–2 GB: 16 cores sin límite de cgroup agotan la RAM (obs #479).
- En worktree: `env -u RUSTC_WRAPPER -u RUSTUP_TOOLCHAIN` (sccache rompe el parseo de `--json` en target dirs aislados y su cache estaba al 10/10 GiB) y `CARGO_BUILD_JOBS=2` + `RUSTFLAGS="-C link-arg=-Wl,--no-keep-memory -C link-arg=-Wl,--reduce-memory-overheads"` porque los links de test binaries mueren por OOM si no (obs #865).
- Receta de contención validada: `systemd-run --user --scope -p MemoryMax=16G -p CPUQuota=400% bash -c 'CARGO_BUILD_JOBS=6 cargo …'`. Gotcha: `CPUQuota=50%` es la mitad de UN core; para techo multi-core hay que pasar de 100% (obs #479).
- Preferencia del dueño: **máx 2 agentes simultáneos** y los gates de cargo **en serie**, nunca dos a la vez (obs #442, scope personal).

Requisitos:

1. El harness **no ejecuta el gate real contra el workspace**. Conduce `scripts/ci_fast_gate.sh` contra un **repo fixture sintético** creado en un `mktemp -d` **fuera del worktree** (nunca dentro; nunca `../` a otra worktree). El fixture lleva su propio `scripts/` con las copias de `ci_fast_gate.sh` y `ci_path_classifier.sh`, y su propio `.git`.
2. **Todo** lo que el gate invoque en los lanes ejercitados va stubbeado en el `PATH` del fixture: `cargo`, `rustfmt`, `cargo clippy`, `cargo nextest`, `cargo metadata`, y lo que aparezca. El harness debe **asertar** que no compiló nada, no suponerlo: `CARGO_TARGET_DIR` apunta a un dir scratch vacío y tiene que **seguir vacío** al terminar, y el log de stubs tiene que mostrar que toda invocación de cargo fue al stub.
3. El harness **no necesita la red** ni ejecuta ningún `cargo` real contra el workspace. Si una invocación real resultara imprescindible, tiene que ser: (a) un comando que **no compila** (`cargo metadata --locked --offline --format-version 1 --no-deps`), (b) dentro de `systemd-run --user --scope -p MemoryMax=16G -p CPUQuota=400%` con `CARGO_BUILD_JOBS=2` y `env -u RUSTC_WRAPPER -u RUSTUP_TOOLCHAIN`.
4. El harness termina en **segundos**, no en minutos: los runners de CI son compartidos. Afirmar un techo (p. ej. < 60 s) y reportar el tiempo real medido.
5. Prohibido, sin excepción: `cargo build`, `cargo nextest run`, `cargo clippy` sobre el workspace, y ejecutar `scripts/ci_fast_gate.sh` real en la raíz del repo (eso es el lane full y reproduce el accidente). El worker tampoco lanza `cargo` en paralelo con nada.
6. El estado scratch (fixture, target dir, stubs) vive en un directorio **en disco**, y **nunca** en `/tmp` si `/tmp` es un tmpfs. En esta máquina `/tmp` es un tmpfs de 16 GB: es RAM. Un target de cargo de 1,9 GB dejado ahí es 1,9 GB de RAM, y eso ya tumbó la sesión del 2026-10-20. Si el scratch necesita un target dir, el target dir va en disco (`$HOME/.cache/…`), no en `/tmp`. El harness reporta sus rutas exactas al padre para que las limpie; no borra el workspace del padre ni toca el `target/` de nadie.
7. El test de S14 se apoya en un **crate fixture mínimo** (una lib con una dependencia por path, sin registry, offline-safe) para probar que con `--locked` un lock desactualizado **fraciesa** el build y el lock en disco queda intacto, y que sin `--locked` el lock se reescribe. El crate tiene que compilar en menos de un segundo y con un solo proceso: es un fixture, no el workspace.
8. **Tope duro para cualquier invocación de cargo**, por mínima que sea: `systemd-run --user --scope -p MemoryMax=2G -p CPUQuota=200%` con `CARGO_BUILD_JOBS=1` y `env -u RUSTC_WRAPPER`. Sin ese scope, un comando que se cuelgue se come la máquina.
9. **Stub de seguridad en el PATH durante todo el harness**: un `cargo` delante del real que se niegue a construir nada, de modo que un `cargo build` accidental sea imposible y no meramente improbable. El cargo real queda alcanzable solo para llamadas que no compilan (`cargo metadata`). Este patrón ya está implementado en `scripts/test_seed_recipe_coherence.sh` (casos 15 y 16) y es el modelo a seguir.
10. **Nunca resolver cargo con `command -v cargo`.** En una worktree eso devuelve `~/.local/share/mbx/bin/cargo`, el shim de **mbx**, un wrapper de caché cuya razón de ser es compilar: pedido un `cargo metadata`, decidió compilar el workspace (1,9 GB de artefactos, 6m33s de CPU y un OOM global que tumbó la sesión). El wrapper es invisible en el argv y en el error, así que la defensa es resolver el cargo del toolchain (`rustup which cargo`, con fallback a `$HOME/.cargo/bin/cargo`) y **negarse a correr** si lo que se resolvió es el shim de mbx. Implementado así en `scripts/test_seed_recipe_coherence.sh`. Para el harness de S15 la respuesta es mejor: **no necesita cargo real ninguno** — todo lo que el gate invoque va stubbeado, incluido `cargo`.
11. **El harness de S15 no invoca `cargo` real, ni mbx, ni el gate real en la raíz del repo.** Corre `ci_fast_gate.sh` contra un repo fixture sintético, en disco, con `cargo`, `rustfmt`, `cargo clippy`, `cargo nextest` y `cargo metadata` stubbeados en el PATH. Las llamadas se asertan por su **log de stubs**, no por el texto del gate.
