## Specs

**S1.** El issue (#1995), verbatim:

> Anchor the automation allowlist on the **whole** co-author name, so a human whose display
> name merely *starts* with an allowlisted token cannot pass the guard.

> `scripts/check_no_ai_attribution.sh` accepts a trailer when the co-author name starts with an
> actor:
>
> ```bash
> [[ "$name_lc" == "$actor_lc"* ]]
> ```
>
> `name_lc` is everything before the `<email>`. So this still passes:
>
> ```
> Co-Authored-By: renovate-bot, actually a human <someone@example.com>
> ```
>
> because the name starts with `renovate`. Same for `release-plz-fan`, `dependabot-wrangler`,
> and any name beginning with `github-actions[bot]`.

Y su criterio de aceptación (verbatim):

> Either:
>
> - the allowlist requires the full name (or an exact `actor` / `actor[bot]` shape), with
>   `scripts/test_no_ai_attribution.sh` extended by a case proving a human name that starts with
>   a token is rejected; or
> - the residual is recorded as accepted, with a one-line rationale in the comment next to
>   `ALLOWED_CO_AUTHORS`, so the next reader knows it was a decision and not an oversight.

Se toma la **primera** rama: el residual es real, se cierra, y no se acepta como deuda.

**S2.** El guard **falla cerrado sobre una allowlist**: un co-autor se acepta sólo cuando
nombra un actor de automatización conocido. Esa regla no cambia; lo que cambia es **cómo** se
compara el nombre. El comentario de `ALLOWED_CO_AUTHORS` ya lo dice: "A new legitimate actor is
a decision made by adding one entry here, never a drift that slips through." Con identidad
exacta, esa frase se cumple de verdad: agregar un actor es agregar **su** nombre.

**S3.** Las identidades de la allowlist son **medidas**, no inventadas: salen de los
co-autores reales del propio repositorio (`git log` de `main`), que son los que el guard
tiene que aceptar para no romper el flujo de release. Cada entrada se escribe en la forma
exacta que el bot estampa (`actor` o `actor[bot]`), y la comparación es **igualdad del nombre
completo**, case-insensitive, con el nombre tomado como la parte anterior al `<email>` y con
los espacios del borde recortados. Un prefijo NO alcanza.

**S4.** Lo que el guard NO cambia: sigue rechazando `Generated with …` / `Generated by …` y el
emoji de robot; sigue escaneando **sólo el bloque de trailers**; sigue siendo fail-closed con
un mensaje vacío; y sigue siendo *forward-looking* (juzga los commits del PR, nunca la
historia). El nombre de un co-autor humano que **empieza** con un token ahora se rechaza:
`renovate-bot, actually a human` no es `renovate[bot]`.

**S5.** El harness es la prueba (D3 del plan padre): el caso nuevo tiene que ser **RED contra
el código pre-fix** por la razón del defecto (el prefijo deja pasar el nombre humano), y
GREEN después. El harness ya existe (`scripts/test_no_ai_attribution.sh`) y **ya está cableado**
en CI (step "AI attribution guard semantics harness"), así que este lote **no toca
`.github/workflows/ci.yml`** y no colisiona con ningún otro lote en curso.

**S6.** Cero builds (regla 3 del plan padre): el lote es shell puro. Ni `cargo check`, ni
`clippy`, ni `nextest`, ni `cargo mutants`. La verificación es el harness + shellcheck con la
misma lista de ignorados que usa CI.

L5 — Verificación del worker (route: `gentle-ai-worker`, surfaces estrechas a los dos

```bash
git log main --format='%(trailers:key=Co-authored-by,valueonly,separator=%x00)' \
  | tr '\0' '\n' | grep -v '^$' \
  | sed -E 's/[[:space:]]*<.*$//' | sed -E 's/^[[:space:]]+|[[:space:]]+$//g' \
  | sort | uniq -c | sort -rn
```

el próximo lector no lo lea como un olvido.
